# Verified learning and self-update

Learning runs only during active authorized work. Preserve the creator/checker boundary and a single shared-state writer. This skill's learning scope is its own workflow and role references; the technical drawing skill uses its separate guarded update procedure. Do not modify unrelated skills, settings or general memory.

Use candidate → scoped validation → independent confirmation → guarded adoption. Each useful record includes `id`, `scope` (invariant/preference/project), `observation`, `cause`, `rule`, `evidence`, `verification`, `behavioral_change`, `visual_change`, `status`, and any superseded ID/reason. Project facts remain in the project's own evidence directory. Shared adopted records contain no private geometry or required external history imports.

An instruction-only refinement may be validated with independent decision cases; label that scope. Changes claimed to improve rendering require actual rendered examples and independent visual checks. Positive/fault cases must exercise the same actual consumer gate, not only a changed assertion or copied expected list. Do not claim a new customer drawing passed just because a skill test passed.

Before updating, take fresh managed-file fingerprints, stage only the needed files, inspect the diff, validate local links and relevant tests, then use the version package's guarded apply/restore helper. A stale fingerprint or active update lock requires reconciliation, not deletion of the lock. Keep complete backups and previous immutable anchors. In-flight runs remain pinned unless the user explicitly changes their scope.

Ordinary cycle addenda do not require a new global Effective Version. The active working skill can evolve through small verified records; frozen Effective Versions remain immutable recovery points. Summarize recent changes briefly with the result and promote a named version only when requested or already authorized.

Current owner defaults (2 + 1 + 2, the requested model profile and clean review presentation) are preferences derived from prior task/test experience. They are not universal proof of optimal speed or guaranteed first-pass quality. New direct user instructions can amend them; preserve supersession without rewriting history.
